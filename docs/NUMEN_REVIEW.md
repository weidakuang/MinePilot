## 结论

Numen 是很有价值的工程参照，但不是可以直接拿来替代本项目执行层的
“已完成答案”。它最成熟的思想是把慢速 LLM 任务和 20 TPS 本地本能拆开，
再让所有本地行为逐 Tick 竞价，同一 Tick 只允许一个行为控制身体。它的
服务端 `ServerPlayer` 身体、异步工具任务、按需 Markdown Skill、分段寻路和
自我中心语义网格，也都与本项目方向一致。

它不适合原样成为本项目基础，原因包括：

- 目标平台主要是 1.21.1 Fabric/NeoForge，而本项目是 Minecraft 26.2、
  Forge 65.x。
- Numen 的扫描、`locate_structure`、`locate_biome` 和未开 GUI 的机器/
  容器检查超过本项目“极限无作弊、只用本人视野”的公平边界。
- 它的战斗本能仍主要是“有武器则追近攻击、低血/无武器则逃跑”，没有覆盖
  本项目要求的持续近战走位、盾牌时机、斧破盾、多目标威胁、药水与复杂 PVP。
- 上游公开 issue 已记录世界冻结、死亡复活冻结、旧坐标、错误完成汇报、
  保存世界卡死、数量统计错误和专用服务器客户端类隔离风险。这些问题必须
  转化为我们的反向门禁，不能把 README 宣称当成验收证据。

## 最值得采用的五个设计

### 1. 单一身体所有权与逐 Tick 行为仲裁

`numen-api` 的 `CompanionBrain` 每 Tick 让全部 `TaskChain` 报优先级，只执行
获胜者；切换时调用旧行为的 `onInterrupt`。Numen 的优先级是：

```text
MLG 10 > 呼吸 6 > 怪物防御 5 > 受伤进食 4
> 饥饿进食 3 > 脱困 2 > LLM任务 0
```

这比“先让技能写一次输入，再让紧急控制器覆盖其中一部分”的隐式规则更容易
审计。对本项目的采用方案不是复制它的类，而是独立实现统一
`BehaviorArbiter`：

```text
候选行为观察同一不可变 TickFrame
        ↓
每个行为返回 Bid(priority, claims, reason, validUntil)
        ↓
按资源域选唯一获胜者
        ↓
只生成一个 BodyIntentFrame
        ↓
一 Tick 租约执行；下 Tick 未续租即停止
```

资源域至少包括移动、视角、主手、使用物品、菜单和载具。紧急行为可以抢占
LLM 技能，但不能让两个控制器在同 Tick 分别转头、移动或挥击。

### 2. LLM 只负责长周期任务，本地反射负责时限动作

Numen 的生存链在本地执行，LLM 任务被抢占时暂停截止时间，危险解除后恢复。
这与本项目既定设计一致，也解释了为什么“让模型每一步都决定”无法得到真人
连续性。模型决定目标、策略、技能选择与异常重规划；落地水、游出水面、格挡、
进食、攻击冷却、受击退让和卡住恢复必须本地逐 Tick 完成。

本项目已经具备 LLM/技能/紧急控制器分层和一 Tick 动作租约，下一步是把它们
统一到显式仲裁器，而不是增加更多并列控制器。

### 3. 异步、分段、有预算的寻路

Numen 使用加权 A*、部分路径提交、提前规划后续段、执行期成本复核以及
逐 Tick 世界快照。这个方向适合长距离移动和低 Tick 开销。本项目应保留自己
的三层路线：

- 全局拓扑：维度、已验证传送门、道路、船、铁路；
- 区域走廊：洞穴、桥、门、入口和安全中间点；
- 局部动作：步行、跳跃、游泳、攀爬、搭路、垫高、挖掘和开门。

不能照搬 Numen 的世界扫描或结构定位；搜索输入只能来自 AI 亲眼观察、实际
走过的路线、玩家明确共享坐标和已打开容器。

### 4. 自我中心语义空间表征

Numen 将附近体素压成以身体为中心的字符/语义网格，而不是把大量裸坐标交给
模型。这适合文本模型理解前后左右、可通行空间和垂直关系。本项目采用同类
原则，但保留：

- 原始观测的遮挡、视锥、距离和时间戳；
- 短期局部 3D 网格；
- 可长期保存的语义拓扑图；
- 与当前身体位置绑定的世界/目标 revision；
- 任何模型回复前重新采样，拒绝“站在村庄却说还在旧森林”的陈旧状态。

### 5. Skill 按需加载与稳定扩展面

Numen 把工作流写成按需加载的 Markdown Skill，并用 API/MCP 给模组提供新
工具。这个思路适合控制上下文和 Token。我们的对应实现应坚持：

- Skill 文本只教流程、前置条件和失败恢复，不直接授予隐藏世界访问；
- `ModAdapter` 暴露配方、菜单和可见 affordance；
- 外部 Codex/MCP 与内置大脑必须显式 acquire/release，不能抢同一身体；
- 模组适配必须按精确版本做契约测试，不能凭注册表名称声称“会用”。

## 明确不采用的部分

| Numen 能力/做法 | 本项目决定 |
|---|---|
| 定位任意结构或群系 | 极限和正常合法生存均禁止；只用观察、地图、眼睛/指令物品的原版反馈或玩家共享坐标 |
| 未开 GUI 读取机器/容器内部 | 禁止读取未亲自打开或未获模组公开可见信息的库存 |
| 大范围服务端方块/实体扫描 | 只允许视距、视锥、遮挡和已加载区块约束下的公平感知 |
| 简单“追到 3 格内站桩攻击” | 只作最小基线；必须增加冷却走位、格挡、后退、侧移、多目标和武器/药水策略 |
| 死后固定在主人旁重生 | 普通生存走原版重生点与掉落恢复；Hardcore 永久失败 |
| 客户端持有主要 Agent Loop | 本项目高层模型和身体控制以服务端世界状态为权威，单人/专服行为一致 |
| 主体/资产直接复用 | 不采用；许可证和项目独立性均不允许静默复制 |

## 上游公开问题转化成的反向门禁

参考：

- https://github.com/Dwinovo/minecraft-numen/issues/12
- https://github.com/Dwinovo/minecraft-numen/issues/15
- https://github.com/Dwinovo/minecraft-numen/issues/9

本项目必须增加或保持以下测试：

1. 每个技能有最大 Tick、无进展计数、目标最后验证时间和结构化失败结果；
   不能对空气、消失实体或旧坐标无限 RUNNING。
2. 任务完成必须绑定世界物理证据，台词和模型自报不算完成。
3. 数量由背包/容器事务前后差计算，不能由模型估算。
4. 每次路径段、攻击目标、容器和建筑位置均带 world revision；过期即重规划。
5. 玩家下线后 AI 仍是正常 `ServerPlayer` 区块票据源；探针必须放在 AI 当前
   区块之外，不能只证明当前区块在 Tick。
6. 保存、重启、死亡、重生、跨维度和取消时释放所有异步任务、数据库句柄、
   Chunk 请求和动作租约。
7. 客户端 UI/皮肤/音频类与专服代码在源码集和加载路径上隔离。
8. 自动跟随是本地持续行为，不要求玩家不断聊天说“过来”；但危险、任务和
   玩家明确“停下”可以抢占。

## 本次审阅已经直接影响的实现

- 真实僵尸突袭门禁曾出现身体 922 Tick、僵尸仅 14 Tick。根因是 Mojang
  `GameTestServer` 的 `PlayerList` 没有应用正式服务器视距/模拟距离，两个值
  为 0；身体跨区块后旧区块实体冻结。实时测试环境现使用 10/10，发布版不
  修改服务器配置。
- 零玩家门禁的实体和方块探针已移到 AI 当前区块之外，证明多区块原版玩家
  模拟窗口，而不是“同区块仍在 Tick”。
- 可信玩家的“身后有僵尸”会触发本地转身扫描和短促潜行分离；看到真实目标
  后才绑定 UUID 并攻击。聊天不能凭空创建一个隐藏实体。
- 近战冷却和命中后会侧移/后撤，真实门禁要求击杀、12 Tick 内物理反应、
  至少 0.35 格位移和逐 Tick 视角平滑同时成立。

## 后续采用顺序

1. 实现统一 `BehaviorArbiter`，先纳入落地水、呼吸、物理接触、投射物、
   进食、脱困、跟随、当前 Skill 和安全空闲。
2. 给所有长技能加入进展证据、目标新鲜度、最大 Tick 和失败回传。
3. 扩展真实聊天门禁：跟随过门/峡谷、村庄事实接地、十僵尸十骷髅、铁傀儡、
   背包物品交接和掉落拾取。
4. 在上述门禁稳定后推进自然随机种子 M1，再进入 M2 通关；不能用受控夹具
   通过数量冒充随机种子统计。
